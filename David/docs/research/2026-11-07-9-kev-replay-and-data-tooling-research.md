## 3. `--max_state` with LoRA at 16K-32K

- `--max_state` range [384, 65536] (`train.py:~455`, `model.py:26,31-38`). `training_context(max_state)`: `max_branch = 1024 + (max_state-384)`, `max_packed = 2048 + (max_state-384)` (`model.py:37-38`). Default 384. README/AGENTS: released checkpoints trained only on 384/1,024 (and <=7,552 in delta stages); "longer inputs are untested for accuracy" (AGENTS.md:427). Serving: 65,536 state / 73,728 packed.
- Kev-4B stage 3/4 precedent: states <=7,552, batch 2x4 accum, gradient checkpointing, one H200: documents stage 43 min peak? card: documents stage 43 min on H200; skills stage 1.4 h on H200, peak 47.7 GB (`kev-4b.md:294-295`). No 4B LoRA data point at 16K/32K in repo. The only long-state memory/speed table is 27B full-weight on 8 H200: single record peak 78 / 96 / 115 / 134 GiB at 16k/32k/48k/64k (1.12 / 2.33 / 3.79 / 5.45 s per record) (AGENTS.md:75-76, `runs/sft-probe/lc-27b-8xh200`, `scripts/sft_probe.py --state_tokens ... --questions 3`). Not transferable to 4B-LoRA; UNVERIFIED for 4B. `scripts/sft_probe.py` is the repo's probe for this (UNVERIFIED flags beyond docs).
- **Critical: `--shared_prefix` defaults to `--full_ft` (=0 for LoRA)** (`train.py:440`: `if a.shared_prefix is None: a.shared_prefix = a.full_ft`). With LoRA and Qwen3.5 (hybrid) the default is the ROW FORM: a record with Q questions runs Q rows of (state+branch), i.e. state cost x Q (`kev/model.py:364-370`, `shared_prefix.py:3-6`). At 16K-32K states pass `--shared_prefix 1` explicitly (hybrid only; exact to row form; tests fp32 ~1e-5; gradient flows through the state; each layer's state+branch step is one checkpointed unit). No LoRA-specific restriction found in `train.py` for shared_prefix. Predictors note: Kev-4B on MLX, 4.8k state x 64 questions = 24.7 GB in one pass vs 8.9 GB one row at a time (`model.py:41-47`) shows row-form blowup.
- `--checkpointing 1` (`train.py:394,546`): HF `gradient_checkpointing_enable(use_reentrant=False)`; all released 4B recipes use it. Shared-prefix path checkpoints per layer.
- `--length_sort 1` (`train.py:187-220`): deals each step's `batch*accum*world` records into micro-batches balanced by padded cost (`--batch` becomes the average). Without `--pass_tokens_max` it costs by CHARACTERS, which caused the round-21 27B OOM (token-dense 5,877-token state set padding of 16 states -> 98.7k-token pass; PLAN.md:795-815). `--pass_tokens_max N` requires `--length_sort 1`, a hybrid backbone (Qwen3.5: yes, `train.py:558-561`), and NOT `--row_budget` or `--perm_kl`; cuts steps on exact token shapes; a single record above N is refused before step 1; 27B used N=40,960 (peak 101.6-108.2 GiB/GPU on 8xH200). For one GPU, compute N from memory; UNVERIFIED value for 4B LoRA.
- `--row_budget N` (one GPU only; not with `--perm_kl`, `--anchor_w`, or torchrun; `train.py:467-471`): padded tokens per forward/backward pass; a record that doesn't fit is split by question. Use only without anchoring.
- `--none_pair_max_state N` + `--p_none_pair`: the released recipe uses `--p_none_pair 0.25`; a none pair repeats the whole state twice more, which tripled a pass past the GPU on long states (AGENTS.md:27-35). Set `--none_pair_max_state` ~2048 (or `--p_none_pair 0`) for long runs; it counts in length_sort cost.
- Delta mode `--init_from`: LoRA + pointer head warm-started; `kev_modal.py:277-283` shows the arg set it passes (base, lora rank, head_dim, lora_targets, option_isolation, special_embeddings, weights_dtype copied from the init checkpoint; base_revision if pinned). Reuse them or training mismatches. Needs `--device cuda --dtype bf16`.
- Timing precedent for long LoRA drift: PLAN.md:2171 "Replay held short states at lr 1e-6" (27B full-FT); LoRA lr for Kev-4B deltas 2e-5.

## 4. Data tooling (`skills/kev-finetune/scripts/`)

- `plan_size.py` (read fully): sizes the EVAL, not train ratios. McNemar paired: `p_d = gain + 2*regressions`; `n = (1.96*sqrt(p_d) + z_b*sqrt(p_d-gain^2))^2 / gain^2`; defaults baseline-acc 0.75, min-gain 0.05, regressions 0.05, power 0.8 (z 0.8416), development 0.15, calibration 0.15. Hand-computed defaults: 469 paired dev questions (UNVERIFIED by execution). With 1 q/record: dev 469 rec, cal 469 rec (>= 100 questions floor), total ~3,127 records, train ~2,189. With 3 q/record: dev 157, cal 157, total ~1,047, train ~733. SKILL.md: "typically ~1000 for three questions per record"; do not settle for 300 (400 rec gave +0.6 pts +-6; 1050 gave +5.9 [+2.3,+9.7]). Prints warning when total > 3000. `--from-result result.json` post-hoc: needs ~10x more records => "too small to chase with volume". No per-option or per-question train count recommendation exists in the script.
- `data-format.md` sizes: 100-200 smoke; 300-600 first real run; 1000-3000 production (consider `--epochs 2`); split 70/15/15; keep >= 40 records in calibration and development. State <= ~1400 chars (384 tokens). Whole request <= 2048 tokens, branch <= 1024 (trainer drops over-limit with count).
- Label balance: `split_data.py:warnings_for` flags any label < 5% of that question form's records ("add more or the model will rarely predict them") and any option with 0 records ("cannot learn options it never sees as correct"); for noul expected {true,false}; for score all indices. Doc says ">= 5% each, ideally roughly equal". Warnings only; no auto-rebalance. `generate_data.py:57-66 batch_targets` auto-balances per batch toward an even split of (done+batch) per option (generation only, not for real data).
- Conflict dropping (`split_data.py:dedupe`, lines ~125-140): drop exact duplicates (same state+questions JSON); a state carrying two different labels for one (qid, type, instructions, criteria) form is a conflict and ALL records with that state are dropped; keyed on normalised state (casefold, whitespace-collapsed sha256). Different rubrics on one state are kept. Split is by state hash (same state -> same partition), seeded shuffle; defaults calibration 0.15, development 0.15, seed 0. `--holdout real.jsonl`: real rows split 50/50 into calibration/development, never trained; every DATA row sharing a state with a real row is dropped from train. Exit 1 if any partition empty ("aim for 300+").
- `split_data.py` validation: types noul/choice/score; choice 1-255 options and label in criteria; score 2-255 levels, label int index; noul label bool; optional `target` soft label must map known keys to nonneg weights. Invalid lines are reported (first 30), not fatal.
- `convert_data.py`: CSV/TSV/JSONL -> records using `workload.json` questions; `--state col[,col]`, `--label qid=col`, `--score-offset 1`, `--map qid="A:x,B:y"`; labels matched case-insensitively; yes/no/1/0 -> noul; unmappable/fractional rows counted and skipped. Reuses `split_data.check_question`.
- `generate_data.py`: LLM (OpenAI-compatible; env `KEV_GEN_API_KEY`/`OPENAI_API_KEY`/`AI_GATEWAY_API_KEY`, `KEV_GEN_BASE_URL`) writes states with target labels; `--n` total (existing valid records count), `--batch 20`, `--examples real.jsonl --n-examples 4`, `--dry-run`. Not needed for our monitor data.
- `kev_modal.py train`: Modal-only (one H100); one epoch default, `--replay 2000`, fits temperature on calibration.jsonl, scores baseline too. We run `kev.train` directly instead.

## 5. Anchors

- `kev/anchors.py` (read lines 1-75): teacher = the FROZEN BASE (e.g. Qwen3.5-4B-Base) zero-shot, NOT Kev-4B. Readout: prompt `"{state}\n{instructions}\nA. opt\nB. ...\nAnswer:"`, softmax over next-token logits of " A".." Z" (<= 26 options; noul -> No/Yes; score -> level texts), batch 16, bf16 on device, `truncation max_length=3072`.
- Exact command (docstring): `uv run python -m kev.anchors --base Qwen/Qwen3-4B-Base --suite evals/v6/decision-v6 --out runs/anchors/v6-4b.json`. Flags: `--base`, `--suite`, `--out` (refuses to overwrite: `FileExistsError`), `--split train`, `--device`, `--revision`. - **Limitation**: `build()` takes `--suite` only (`load_split`); no `--data`. Targets keyed by `_meta.id` (`anchors.py:42`), and trainer looks up `anchors[v.request_id]` (`train.py:355`). To anchor our records, write a small variant that builds `jobs` from `load_records(ours)` (ids `custom/<n>`). UNVERIFIED (simple edit). Question text for long states truncates at 3072 tokens (so useless for 16K+ states).
- Training use: `--anchor path.json --anchor_w W [--anchor_sources a,b]`; must be set together (`train.py:450`); loss `anchor_w * KL(teacher||student)` per anchored question, averaged per variant (`train.py:64-70, 355-358`); skipped for a question when the option set changed (none-option inserted; `anchor_loss` returns None if keys differ). Not with `--row_budget`. Example arms: `experiments/anchor-4b-v6.json` (anchor_w 0.3/0.5/1.0; sources arc,openbookqa,csqa; lr 5e-5; Qwen3-4B).
- Cost: a forward-only pass over decision-v7 train questions (15,576 q; each prompt < 3072 tokens) on one GPU, batch 16 => ~974 batches; minutes on an H100 (UNVERIFIED wall time; no timing in repo). Training cost: one extra softmax/KL per question, no extra forward.
- Verdict from the authors: "anchoring toward the base's answers ... not a lever" (PLAN.md:269, 3179, "Toward v0.2"); anchoring targets the BASE, so it would pull toward base zero-shot behavior (not toward Kev-4B's behavior); a KL toward the released model's own served answers on replay records was proposed but needs a different builder (PLAN.md:2764-2765: "`kev.anchors` today targets the frozen base's zero-shot answers; this needs the released model's distributions"). For our use (preserve Kev-4B), replay + low lr is the documented lever; a self-distillation anchor would need a custom builder.

## Quick recipe synthesis (from the above, not tested)

```
# fetch happens automatically on first load_split; or: hf download jaredpalmer/kev-suites v7/decision-v7/train.jsonl --repo-type dataset
uv run python -m kev.train --init_from jaredpalmer/kev-4b --data ours/train.jsonl \
  --suite evals/v7/decision-v7 --replay N --max_state 16448 --epochs 1 --lr 2e-5 --batch 1 --accum 8 \
  --dtype bf16 --device cuda --checkpointing 1 --shared_prefix 1 --length_sort 1 --pass_tokens_max <GPU-sized> \
  --p_none_pair 0.25 --none_pair_max_state 2048 --seed 1 --out runs/monitor-v1
```
Also pass base/lora/head_dim/lora_targets/base_revision from the init checkpoint (see `kev_modal.py:277-283`). Replay share: mimic releases (0.35-0.4x of task records; but PLAN says hold the SHARE ~25-30% when mixing in long examples). Replay samples are short (<=384 tokens), so the long examples are 100% ours.
